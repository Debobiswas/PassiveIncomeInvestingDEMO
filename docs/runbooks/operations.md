# F6 operations and staged release

Status: locally implemented/tested; **not deployed or accepted**. This runbook is not authorization to create resources, upload artifacts, migrate a remote database or promote production. Work from the repository root with Node/npm versions in `.nvmrc`/`package.json`.

## Target and ownership record (required before hosted work)

Record approved Vercel team/project, Supabase project ref, Sentry organization and browser/API projects, staging domain, release owner, incident responder, approval date, budget owner and retention policy. These selections are currently unresolved. Do not infer the target from whichever CLI account happens to be logged in.

- Use an isolated **staging Vercel project** with staging-only Supabase and Sentry targets. A dedicated project allows exercising its production-domain rollback semantics without touching the customer production project. Do not use production DB/Auth credentials in previews, forks or untrusted pull requests.
- `vercel.json` pins functions to `iad1` (Washington, DC). Pair with an approved North American Supabase region, preferably nearby; verify actual compute placement and project database region in provider evidence before acceptance. A config file is not proof of deployment. CDN delivery, Auth/email/Google, logs/backups and third-party processing are distinct from database/function location. See [Vercel regions configuration](https://vercel.com/docs/project-configuration/vercel-json#regions) and [Supabase available regions](https://supabase.com/docs/guides/platform/regions).
- Use root workspace settings, the committed lockfile, Node 24, `npm ci`, root `npm run build`, output `apps/web/dist`. Never deploy the workspace-only Vite build: the root build removes private maps and applies artifact/configuration gates.
- Disable automatic production promotion until required CI checks, environment protection and a human release approval are verified. The workflow alone does not enforce branch protection. Keep deployment source/log visibility private and preview access protected.

## Configuration and secrets

Set these in the approved environment's secret store; do not paste values into evidence, shell arguments, screenshots or chat. Root `.env.example` documents server settings; `apps/web/.env.example` documents public settings. Local Node scripts do not auto-load `.env`; supply variables through the process environment or Node's approved env-file mechanism.

| Setting                                              | Scope                            | Rule                                                                               |
| ---------------------------------------------------- | -------------------------------- | ---------------------------------------------------------------------------------- |
| `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY`           | API                              | Approved staging target; no service-role key needed                                |
| `VITE_SUPABASE_URL`, `VITE_SUPABASE_PUBLISHABLE_KEY` | Browser/build                    | Same target/key as API; publishable only                                           |
| `SENTRY_DSN`, `VITE_SENTRY_DSN`                      | API / browser                    | Approved US-ingest DSNs; may identify separate projects                            |
| `PII_RELEASE`, `VITE_PII_RELEASE`                    | API / browser/build              | Identical full 40-character Git commit SHA                                         |
| `PII_ENVIRONMENT`, `VITE_PII_ENVIRONMENT`            | API / browser/build              | Identical `staging` or `production`; local telemetry opt-in uses `local`           |
| `PII_READINESS_KEY`                                  | API + monitor                    | Separate randomly generated 32–128 character URL-safe secret; rotate independently |
| `SENTRY_AUTH_TOKEN`, `SENTRY_ORG`, `SENTRY_PROJECT`  | Private artifact upload job only | Never `VITE_*`, runtime, browser bundle or public artifact                         |
| `PII_SMOKE_URL`, `PII_SMOKE_ACCESS_TOKEN`            | Smoke process only               | Explicit HTTPS origin and short-lived synthetic non-staff session                  |
| `VERCEL_AUTOMATION_BYPASS_SECRET`                    | Protected preview smoke only     | Sent as header, never query string; not a browser setting                          |

Hosted root builds (`VERCEL=1`) fail on missing/inconsistent release/telemetry/backend settings; `PII_REQUIRE_RELEASE_CONFIG=1` exercises that gate outside Vercel. Locally absent telemetry config makes no monitoring requests. Invalid runtime telemetry config is best effort/no-op rather than an application outage; hosted builds must prevent it. Supabase URL/key consistency is not proof of region or isolation. Keep Google disabled until the actual OAuth client and exact redirect allowlist pass the hosted F5 journey.

## Health and readiness

- `GET /api/health`: public process liveness only. Returns `{ "status": "alive" }`; makes no backend call and is never evidence of DB/Auth availability.
- `GET /api/ready`: requires `X-PII-Readiness-Key` **and** a current synthetic-member Bearer token. Missing/wrong/unconfigured key returns empty 404 without touching dependencies. Wrong method returns 405 only after the key gate. Probe verifies Auth identity, owned profile and onboarding RPC response contracts through real RLS. It never initializes or changes records. Return 200/`ready` only after these reads; failure/expired session/missing profile returns generic 503/`not_ready`, with request ID but no configuration or backend error detail. Five-second dependency deadline; at most another 500ms for monitoring flush. Responses are private/no-store.
- Initialize the dedicated synthetic user's profile through normal onboarding before monitoring. Keep it non-staff, use no real holdings, and refresh its short-lived session in a protected monitor. An expired monitor token is a failed probe, not automatically a database incident. Do not disable session validation to make the monitor green.
- Start at a low probe frequency (e.g. once per minute), with a small failure threshold and named responder. No public expensive probe, no synthetic sign-in storm. Readiness does **not** prove email/Google, approved disclosure, tenant-isolation coverage, capacity, a worker, or product acceptance.
- Manual local API: `npm run dev:api`. Automated integration tests construct the same handlers against the isolated PII local stack; no remote reset is used.

## Monitoring privacy and source maps

Pinned Sentry 11 clients use no default integrations, no replay, no breadcrumbs, no tracing/propagation, no log/metric delivery and explicit `dataCollection` opt-outs. The final `beforeSend` reconstructs events from enum-valued kind/route/code, optional request UUID, release and environment. Arbitrary exception messages, user/IP fields, URLs, cookies, headers, bodies, holdings, prompts, locals and scope extras are discarded. Browser reports can retain bounded `app:///assets/<build-file>.js` line/column locations, never original host paths, query strings, function names or source context. Browser failures are capped at 20 per page load. API reports currently provide safe failure category/request correlation, not original server exception stacks. Adding symbolicated server stack locations requires a separate reviewed deployed-function artifact adapter before claiming full M1-R04 source-map acceptance.

The API creates the request UUID; a failing member request reports the same UUID in browser telemetry. Expected 4xx denials do not generate API error events. Monitoring is best effort and must not replace a safe API response. A serverless request awaits up to 500ms of SDK flush, not an unawaited background promise. Never add `console.log(error)`, global scopes with user details, replay or raw provider logging as a debugging shortcut. Sentry and hosting still receive transport metadata; configure provider-side IP removal, access control, retention and quota alerts. SDK payload redaction is not a promise that every provider log is free of metadata.

`npm run build` generates hidden browser source maps and moves them to ignored `.private-artifacts/source-maps/<release-or-local>/`, outside `apps/web/dist`, with asset/map SHA-256 manifest and restrictive permissions. The build fails if a `.map`, PDF/XLSX or reference directory remains public. Vite denies access to the private archive; `.vercelignore` excludes local private artifacts and reference originals from CLI uploads. Do not upload the repository, client documents, env files or broad directories as Sentry artifacts.

Before hosted acceptance, configure a private, pinned Sentry upload job for **the same build artifact and SHA**. Upload corresponding generated JS/maps with `app:///assets` naming and release association, then verify a real browser error resolves to the expected source line. Do not inject/debug-rewrite deployed files after recording their hashes. Current code supports release-based filename matching; debug-ID adoption must preserve the privacy filter and artifact identity. No upload credentials or automatic upload job have been enabled yet. See [Sentry release/source-map CLI](https://docs.sentry.io/cli/releases/) and [SDK 11 data-collection changes](https://docs.sentry.io/platforms/javascript/migration/v10-to-v11/).

For a tagged smoke, use a dedicated synthetic browser session and induce a controlled failed lazy-route fetch in a local test harness pointed only at approved staging. For API telemetry, use a disposable staging test deployment with deliberately unavailable upstream configuration, not a public throw endpoint or an outage in the shared staging project. Match response/browser/API request IDs and release in Sentry, inspect the stored event for redaction, verify alert receipt and restore the test deployment. Unit envelope tests and intercepted browser envelopes are not evidence of hosted ingestion.

## Release, smoke and rollback procedure

1. Confirm exact target IDs/region/isolation, approved access, migration inventory and restore owner. Inspect whether real data exists. No destructive remote resets. F6 has no schema migration; earlier F4 migration still needs an approved hosted replay/upgrade plan, backup and restore evidence. Prefer additive migrations compatible with current and previous app versions.
2. On a clean reviewed commit run `npm ci`, `npm run check`, `npm run test:e2e`, `npm run test:operations:e2e`; against disposable local PII data run `npm run db:check`, `npm run test:integration`, `npm run test:auth:e2e` serially. CI also replays the migration from scratch. Obtain the actual green run links and required-check enforcement; do not infer those from local results.
3. Record candidate SHA, exact artifact digest/manifest, target IDs, configuration version (not secrets), schema version, prior known-good deployment and last backup/restore test. Build with consistent release variables and private source-map handling. Resolve source-map upload/symbolication and alert gates before member release.
4. With explicit approval, deploy that artifact to the protected **staging project**, inspect function regions and verify API routing. Never attach production secrets just to get a build passing.
5. Supply smoke variables from a protected environment and run `npm run release:smoke`. It performs read-only probes, sends credentials only in headers, refuses redirect following, checks unauthenticated API denial, protected readiness, release equality, deep links and security headers. It prints only sanitized pass/fail and the release. HTML checks are not browser Auth acceptance; also run hosted email/Google/member journeys with designated test accounts.
6. Rehearse **A → B → A** on the staging project's domain: start from known-good compatible A, deploy candidate B, verify B, invoke the approved provider rollback to A, verify A's original SHA through the same smoke, and confirm a synthetic saved profile survives. Record timestamps, deployment IDs, smoke artifacts, schema compatibility, observed recovery time and reviewer. Do not fabricate a passing rehearsal from code tests.
7. Production promotion is separate approval after all release gates. [Vercel Instant Rollback](https://vercel.com/docs/instant-rollback) restores a previous deployment/configuration, not the database or changed external providers. Verify old credentials/config still work. If schema is incompatible, use a reviewed forward repair; do not roll back data by reset. Record whether automatic domain assignment remains disabled after rollback.

## Incident response

First classify: identity outage, application regression, monitoring-only outage, dependency latency, or suspected cross-user exposure. Record UTC time/release/request IDs, never tokens or private screenshots. Stop promotion. For suspected exposure, restrict affected entry points immediately and escalate to the named security/incident owner; preserve access-controlled evidence. For regressions use the compatible known-good artifact, then verify health/readiness and a synthetic member journey. For expired synthetic credentials refresh the monitor session securely; do not relabel a failing probe healthy. Communicate impact, recovery and unresolved risk. Restore drills happen on a separate approved target, never over the only live database. Capacity remains governed by `docs/rebuild/CAPACITY_AND_RELIABILITY.md`, not a green health check.
