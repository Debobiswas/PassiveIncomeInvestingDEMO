## Outcome and scope

A user can discover a real, traceable fund, narrow the catalogue on a phone, compare at most three distinct listings, and open its educational deep dive. A designated administrator can safely maintain the catalogue. Other milestones consume the same versioned fund and model-portfolio identities.

Contractual scope: schema for 140+ ETFs; one-time import from Client Excel Tab 4 plus sample portfolios; mobile-first filter UI; side-by-side comparison of up to three ETFs; deep-dive screen with embedded YouTube links; admin add/edit/remove ETFs.
Engineering additions proposed to make those deliverables reliable: stable listing identities, provenance, validated staged imports, atomic publication, audit records, bounded queries, versioned read contracts, authorization tests and rollback. These are implementation safeguards, not extra contractual product features.
Non-goals: trade execution, broker synchronization, personalized AI recommendations, RAG ingestion, sponsorship administration, recurring web scraping, premium market-data procurement, or blindly importing all 497 master-list rows.
M2.5b owns distribution history, payout dates and calculated yield. M4 owns generating and saving personalized portfolios. M2.5a imports the Client-authored model portfolios they consume.

## Primary journey and states

1. Open `/app/funds` with query and filter state in the URL. Read current catalogue version and source/freshness label. The navigation label may be Explore; route ownership follows `../ARCHITECTURE.md`.
2. Search ticker/name; filter by listing country, currency, issuer, covered-call classification, distribution frequency and sector/region where supported. Final v1 filter set needs product signoff; the contract does not enumerate it.
3. Select up to three listings, preserving order by stable ID. Open `/app/funds/compare?ids=…`; present labeled values, units, currencies and unavailable values consistently.
4. Open `/app/funds/:listingId`; review sourced attributes, dated commentary, related Client content and a link back to the same results.
5. Administrator opens `/admin/funds`, validates an edit, reviews its impact and publishes. Removal unpublishes/archives the record; historical consumers retain its identity and revision.

Loading preserves layout; empty catalogue differs from no filter results. Request errors offer retry without resetting filters. Unknown/archived deep links explain status rather than redirecting silently. Expired sessions preserve a safe return path.
Unknown attributes are explicitly unavailable. A stale source date is visible; yield filters must not quietly exclude unknowns without explaining their treatment. A failed YouTube embed has a normal external link.
Use semantic form controls, visible focus, accessible names and announced result/selection changes. Comparison must remain understandable with keyboard and screen reader navigation, horizontal scrolling or stacked labeled cards. Do not communicate superior values through color alone.
Admin pending/conflict/invalid/forbidden states distinguish validation from permissions. An optimistic-concurrency conflict displays the current revision and requires a fresh edit preview; never overwrite silently.

## Modules, APIs and ownership

Proposed modules: `catalogue` owns identities, fund facts and publication; `model-portfolios` owns Client templates and allocations; `catalogue-import` owns workbook parsing/mapping/staging; `catalogue-admin` orchestrates authorized commands. Shared contracts contain transport types and runtime schemas, not browser-only or database-specific imports.
The web module handles route/query state and presentation. HTTP controllers authenticate, validate and delegate to services; repositories encapsulate queries. A bounded worker parses source artifacts and resolves links without blocking web request lifetimes. No service-role credential reaches the browser.

| Conceptual entity | Responsibility and constraints |
| --- | --- |
| Fund / Listing | Stable fund identity plus tradeable listing identity; exchange/MIC, symbol, currency and effective dates; symbol alone is never a global key; an issuer is separate from a sponsor-format adapter |
| FundRevision / CatalogueRelease | Immutable revision of sourced attributes, publication status, author and timestamps; release pins a consistent visible revision set |
| SourceArtifact / SourceReference | Original SHA-256, version, workbook sheet/row/cell, URL, captured/effective timestamps; uploaded artifacts private to administrators |
| FundAttributes | Name, issuer, fee with `feeType`, frequency, strategy, covered-call/leverage classifications and factual categories; preserve raw value plus normalized value and mapping version |
| EditorialAnnotation / FundContentLink | Client opinion, author/source/date, approved YouTube URL/video ID and fund association; separate opinions from factual metrics |
| ModelPortfolio / ModelPortfolioRevision | Stable template and country/strategy/variant; source title and explanatory text; immutable constituent listing IDs and decimal weights plus any explicit cash allocation |
| ImportRun / StagedRow / AuditEvent | Artifact/mapping version, status, errors and reconciliation; actor, operation, prior/new revision, request ID; no entire source payload in ordinary logs |

Proposed versioned endpoints follow the application-wide API conventions decided by M1:

- `GET /api/v1/funds`: validated query/filter/sort, cursor and capped limit (proposed 50); returns items, applied filters, release ID, as-of and freshness. Sorting uses a stable ID tie-breaker.
- `GET /api/v1/funds/:listingId`: published detail, factual versus editorial sections, source references and approved content links. Never exposes admin draft fields.
- `GET /api/v1/funds/compare?ids=…`: one to three unique IDs, consistent release snapshot, labeled field definitions and nulls. The UI encourages two or three.
- `GET /api/v1/model-portfolios` and `/:id`: published Client templates and immutable revision IDs; does not return users' saved goals or generated plans.
- Admin commands create/edit/archive with expected revision and request idempotency key; publishing is explicit. Staged import endpoints start a run, read reconciliation and publish a validated run. Final route spellings belong in M1's API registry.
- Error codes distinguish invalid input (400/422), denied access (403), missing/archived entity (404/410 as agreed), revision conflict (409) and retryable dependency failure (503).

Published catalogue access follows the product's public-versus-signed-in policy; default planning assumption is signed-in app access. Public access, if approved, uses only a published projection with no user data.
Admin authorization is server-enforced from trusted roles, not profile fields editable by users. Database privileges and RLS enforce the same boundary. Worker access is scoped to ingestion services; private portfolio access is unnecessary.
No shared response or cache key contains account holdings, user goals or private questionnaire answers. User-specific endpoints cannot reuse a public catalogue cache policy.

## Import and publication contract

`original workbook → parse/stage → normalize/resolve identities → validate/reconcile → admin review → publish release → invalidate caches / emit CataloguePublished`

The preserved workbook hash is `66ea19a3a6adf813d7d3999b4c5202815566be69270c2e875f7fb58e72b077be`. The named Tab 4 is `4- U.S. Covered Call ETF Guide`, not the fourth sheet by position; inventory reports 144 symbol-bearing rows. Resolve duplicates and malformed records before claiming coverage.
Canadian and U.S. sample sheets each contain seven core intents plus variants. Inventory row counts do not prove exact model counts. Parse heading/merged-cell structure and charts against actual cells; manually review ambiguous variants and allocations.
Some model constituents are outside Tab 4. Resolve them from the supplied broader catalogue/Canadian guide with explicit source lineage; classify non-ETF holdings correctly. An unresolved constituent blocks that template's publication, never becomes an invented fund or disappears from its weights.
Use deterministic source/mapping keys so repeated runs are idempotent. Never execute workbook formulas or visit arbitrary cell URLs during parsing; parse approved hyperlink types as data. Formula-derived source values need recorded interpretation and test fixtures, not blind trust in cached cells.
Validate identity, currency, category mapping, decimals/ranges, source links and allocations. Proposed tolerance: allocation weights sum to 100% within 0.01 percentage point; report deviations and preserve original values rather than silently normalizing. Agree any cash/residual convention with Client.
One-time bootstrap can be a tested worker/CLI plus basic admin review; do not build a general sponsor upload product here. M2.5b owns its recurring distribution upload/diff workflow and may reuse staging/publication primitives.
Publication uses a transaction to switch the active release after all prerequisites pass. Concurrent admin edits require revision checks. `catalogue.published.v1` and `catalogue.fund_archived.v1` events include release/revision IDs; delivery retries are idempotent and cannot roll back the successful database commit.

## Dependencies and downstream guarantees

- M1 must supply routes, trusted admin roles, typed API conventions, schema migrations, secrets, storage, job execution, observability and deployment gates. Catalogue identity/schema work can proceed alongside M2 once those contracts are stable.
- M2 supplies broker symbol/identifier observations; it consumes catalogue identity resolution. Unmatched holdings remain valid private holdings and are labeled unresolved, never forcibly matched by ticker.
- M2.5b receives immutable listing IDs, issuer/source aliases, publication states and currency. It owns issuer distribution events and yield definitions; broker cash receipts remain a different domain. Screener yield/date fields use its projections and keep null/stale status.
- M3 receives source/versioned assumptions and optional M2.5b yield metrics. Workbook illustrative target yield is a scenario input, not observed return; no MER/management-fee substitution or tax residency inference from listing country.
- M4 receives exact model-template revisions, valid constituent IDs, normalized categories and published eligibility. Generated plans pin revisions and never silently mutate after an admin edit or archive; M4 owns subsequent suitability/risk constraints.
- M5 receives approved content links, source/cell references, factual/editorial distinctions and release events for reindexing. It must not index admin drafts or treat workbook text as instructions. A vector index is not the authoritative current fund database.

## Verification, performance and release

Domain fixtures include duplicate ticker across exchanges; symbol change; unknown currency; missing fee; management fee versus MER; monthly versus variable payout; unknown yield; archived listing; broken video; same workbook retried; unresolved and non-ETF model constituents; allocation sum violation.
Integration tests use a real isolated database and storage/job adapter: draft read denial, ordinary-user write denial, forged role rejected, atomic release failure, stale expected revision, archive with saved references, cache invalidation retry and deterministic reimport. Two users' unrelated private records must never appear in shared catalogue APIs.
Browser E2E imports the fixture dataset through real admin operations, publishes, then filters/compares/opens deep links as a normal user; exercises direct navigation, refresh, 360px layout, keyboard focus and unavailable embeds. UI-only mocked tests do not establish completion.
Use the canonical beta workload in `../CAPACITY_AND_RELIABILITY.md`: 2,500 users / 1,000 simultaneously online, proposed 100 aggregate reads/s + 10 writes/s and a 400-read/s reconnect burst; catalogue reads are part of that mix. Additionally seed 10,000 catalogue listings for data headroom and record cold-cache queries separately. Shared read/error/connection gates apply; these are proposed tests, not evidence of 300,000-user capacity. Apply `../PRODUCT_EXPERIENCE.md` for readable mobile/web parity and enlarged-text behavior.
Read-only catalogue growth primarily scales through bounded queries and versioned caches; do not queue one refresh job per user. Limit uploaded source sizes, worker concurrency and retries. Lazy-load admin parsers and video embeds to avoid making every visitor download ingestion tooling.
Instrument import duration/error counts, unresolved identities, unpublished exceptions, publish conflicts, release propagation lag, API p95/p99, cache hit rate and origin-query count. Alert on a failed publication job or unexpected empty active catalogue; log IDs and counts without private payloads.
Release requires all contractual acceptance evidence, agreed engineering gates, source reconciliation approval, working admin demo and a rehearsed prior-release rollback. Published counts, source dates and unsupported data must be visible in the demo, not concealed by fixtures.
Rollback switches active catalogue release and invalidates matching caches; retains prior revisions/IDs referenced by plans and distribution data. Backward-compatible response additions are preferred; breaking identity/field semantics require an API version/migration plan and consumer review.
