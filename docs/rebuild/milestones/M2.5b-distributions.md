Status: proposed implementation PRD; not implemented or accepted.
Authority: signed agreement, §2.1, pages 1–2, M2.5b, $3,000 CAD. The title “Live” does not name or procure an automatic market-data provider.
Baseline: `master` at `4dbf440` and the independent `feat/portfolio-import` worktree. Contract text was checked directly on pages 1–2; workbook coverage comes from `docs/reference/README.md`.

## Outcome, scope and interpretation

A member can inspect a fund's published distribution history, understand its stated yield and dates, and tell how fresh and complete the information is. An authorized administrator can publish a sponsor file only after reviewing validation errors and the precise changes it would make.
Signed coverage: 12–24-month distribution history data model; distribution charts; current yield, last distribution and ex/record/pay dates; admin CSV/XLSX upload with schema validation and diff preview; sponsor format normalization.
Proposed engineering gates: provenance, canonical identity, decimal arithmetic, versioned metrics, atomic publication, access controls, audit history, bounded uploads and repeatable tests. They make the contracted workflow reliable; they do not add a sponsor advertising dashboard.
Non-goals: trade execution, personalized recommendations, tax reporting, automatic entitlement determination, exchange price feeds, recurring crawlers, or fabricated distributions for missing months. User cash receipts belong to M2; forecast income belongs to M3.
The supplied workbook is a curated catalogue and contains no demonstrated 12–24-month fund event dataset. Historical sponsor files, accepted source formats, source-use rights, maintenance owner and price inputs are external prerequisites, not implementation details to conceal with fixtures.

## User and administrator journeys

1. Open `/app/funds/:listingId/distributions` directly or from a fund/portfolio. A portfolio shortcut selects fund identities but does not turn announcements into actual receipts.
2. Read the current metric with its method and price date, last paid distribution, and next announced ex/record/pay dates. Short explanations expand “ex-dividend” and “record date”; neither implies this user is entitled to payment.
3. Select 12m or 24m and inspect the chart or equivalent table. Display complete dates/year, amount per unit and currency. A month may have several events; drilldown preserves each one.
4. Administrator opens `/admin/distributions`, chooses sponsor format and upload scope, uploads CSV/XLSX, waits for bounded parsing, resolves errors and reviews the diff. Publication is a distinct explicit command.
5. Following successful publication, the same member URL shows the new release and its freshness label. An administrator can inspect provenance and return to a prior valid release without editing source history.

Loading retains the selected fund/range. No history, incomplete history, a new fund, a real zero payout, no upcoming announcement, stale data and a failed request are separate states. Retry does not reset the user's selection.
Cancelled/corrected records are traceable. Unknown identity is quarantined; it is not assigned by ticker alone. A failed upload keeps the existing published dataset. An expired admin session preserves only a safe job reference, not a sensitive file in browser storage.
Mobile is the primary product, with equivalent web capabilities for users who prefer larger screens. Proposed baseline: 16px body text, readable chart labels/table alternative, 44px primary touch targets, sufficient contrast, visible focus and no essential hover-only details. Verify at 360px width and 200% zoom/text enlargement; accommodate platform text scaling in M8.
Charts cannot use color alone to identify series or communicate gaps. Desktop density must not produce the existing 9–11px essential labels. Announce upload status/errors and move focus predictably to validation summaries.

## Domain definitions and financial rules

| Concept | Proposed definition / invariant |
| --- | --- |
| Listing identity | M2.5a stable listing ID, currency and exchange/share class; a ticker is an alias, not a global identifier |
| Distribution event | Published per-unit declared cash amount, explicit currency, event classification, ex/record/pay calendar dates, status and source; never a user cash ledger row |
| Dates | Sponsor calendar dates stored as dates; ingestion/publication timestamps are UTC instants. Retain source locale/timezone and date parser version. Reject ambiguous `03/04/26` unless adapter specifies interpretation |
| Last distribution | Proposed display means most recent noncancelled event whose pay date is on/before the as-of date. A newer announcement is labeled separately. Missing pay date means payment status is unknown |
| Trailing 12-month yield | Sum eligible published cash amounts with pay dates in `(asOf minus 12 calendar months, asOf]`, divided by a compatible price, multiplied by 100; disclose inclusion of special payments and coverage completeness |
| Annualized latest regular yield | Last eligible regular per-unit payment × known annual frequency ÷ compatible price × 100. Label as annualized estimate; variable/unknown frequency or special-only history does not support this formula |
| Current yield | Product must choose one primary method above before implementation. API returns `metricType`, inputs, formula version, price ID/date and distribution release ID; it must not silently change methods when data is missing |
| Price observation | Explicit amount/currency, per-unit/share basis, source, observed market date/time, price type (e.g. close) and correction version. Price must be positive and compatible with distribution currency and split basis |
| Actual receipt / yield on cost | M2 cash activity / a separate cost-based calculation; neither equals shared fund yield. Do not infer received income or tax treatment from announcements |

Use decimal arithmetic and explicit rounding at display boundaries. Proposed independent examples: CAD 0.10 paid monthly with CAD 20 price gives a 6% annualized estimate; twelve CAD 0.10 payments plus CAD 0.40 special yield 8% trailing cash yield at CAD 20, not the same metric. A USD payment with a CAD price is unavailable without an explicit approved conversion method/rate/date.
Corporate actions require a common per-unit basis across historical amounts and current price. Store adjustment provenance or mark the metric unavailable; never compare pre-split distributions directly with a post-split price. This condition must be covered even if automatic corporate-action ingestion is deferred.
Incomplete history cannot be presented as a complete trailing yield. Missing months remain gaps, while an explicitly sourced zero payout is a real zero. Tax character, return of capital and reinvested/noncash amounts need source classification and agreed inclusion rules; never infer them from a large payout.
No user receipt totals combine CAD and USD without identified FX inputs. A shared chart can separate currency series; it cannot hide both behind an unlabeled `$` axis.

## Data, APIs and ownership

`distribution-ingestion` owns source adapters/staging; `distributions` owns event revisions, publication and coverage; `yield-metrics` owns deterministic calculations and input provenance; route components only orchestrate UI.
Conceptual records: `SponsorFormatVersion`, private `SourceArtifact`, `DistributionImport`, `StagedEvent`, immutable `DistributionEventRevision`, `DistributionRelease`, `HistoryCoverage`, `PriceObservation`, `YieldSnapshot`, and audit/outbox events. Reuse M1 job/storage conventions and M2.5a canonical listing/source identities rather than duplicating issuers.
An event's stable identity prefers source event ID scoped to sponsor/listing. Without one, an adapter defines a documented composite identity plus correction matching. Same pay date alone cannot distinguish regular and special payments. Ambiguous identity is a conflict, not an automatic overwrite.
Retain event revisions and prior published releases for audit/rollback; a default 24-month UI window does not authorize deleting older records. Retention of raw uploads and historical revisions is an explicit operations policy.

| Proposed API | Responsibility |
| --- | --- |
| `GET /api/v1/funds/:listingId/distributions?range=12m|24m` | Published events, chart groups, last/next records, coverage, release and freshness; stable ordering and bounded response |
| `GET /api/v1/funds/:listingId/yield` | Named metric, value or unavailable reason, input versions/as-of and provenance; one shared implementation for screener, detail, web and mobile |
| `POST /api/v1/admin/distribution-imports` | Authorized bounded upload reference, sponsor adapter/version, source scope and idempotency key; returns owned job resource |
| `GET /api/v1/admin/distribution-imports/:id` | Status, validation summary and paginated diff; administrators only |
| `POST /api/v1/admin/distribution-imports/:id/publish` | Reviewed diff digest, expected base release and idempotency key; publishes atomically or returns conflict |
| `POST /api/v1/admin/distribution-releases/:id/restore` | Authorized audited activation of an existing valid release; no destructive rewrite |

Published reference reads follow M1/M2.5a access policy. User-specific portfolio aggregation uses a separate authorized endpoint/cache; no private holdings enter shared CDN responses. Trusted roles control every admin command; browser route guards are insufficient.
Raw artifacts, staging rows and error reports are private. Workers obtain only required ingestion privileges. Server and database tests separately prove allowed access and denial. Distribution publication does not require access to brokerage credentials or user portfolios.

## Ingestion, diff and publication

`private upload → parse with explicit adapter → normalize/resolve → validate → immutable diff → admin publish → transaction + outbox → refresh shared projections`

Proposed initial limits, to benchmark and document: 10 MiB compressed input, 50 MiB expanded XLSX, 100,000 populated rows, bounded sheets/cells and parse deadline. Reject encrypted/macro-capable inputs for this CSV/XLSX workflow; inspect file signature and archive limits rather than trusting extension. Do not execute formulas, external links or embedded instructions.
Adapters define required/optional columns, locale, decimal separators, amount units, date formats, sheet selection, source currency rules and event classifications. Preserve raw values and mapping version. Formula cells in required numeric fields are rejected or require a separately reviewed value-only source, not arbitrary expression execution.
Validate resolved listing/currency, finite nonnegative per-unit amounts, supported status/type and plausible dates. Date-order anomalies are reviewed under sponsor rules, not automatically “fixed”; missing dates are permitted only with explicit unavailable presentation and metric restrictions.
Diff rows contain source row locator, event identity, old/new values, warnings and reason. Normal uploads are additive/corrective; absence from a file never deletes history. A complete-replacement scope must identify sponsor/listings/date window, prove coverage and present explicit withdrawals for review.
Conflicting duplicates block publish. Exact duplicates are reported as unchanged. Partial publication is excluded initially: fix a file or explicitly scope a new import, then review the complete new diff. Warnings require documented acknowledgment; errors cannot be acknowledged away.
Import identity includes actor/operation idempotency key and request digest; source hash plus adapter version/scope supports deduplication. Reusing a key for different content is a conflict. Retry after a lost response returns the original job/publication result.
Persist normalized staging and its digest before review. Publish checks the active release and digest in the same database transaction that records revisions, switches active release and writes the outbox event. Another publication invalidates the preview; regenerate it instead of applying stale changes.
Read responses pin release/price/metric versions so a cache refresh cannot combine an old amount with an unexplained new formula. `distributions.published.v1` carries release and affected listing IDs. Outbox delivery, metric recomputation and cache invalidation are idempotent; stale cache is labeled until refreshed.
Jobs have bounded retries, lease recovery and terminal states from M1. A poison file cannot starve interactive reads or other imports. Never start ingestion per user page load or make an external sponsor call per chart render.

## Freshness and price-source decision

Default delivery assumption is administrator-published sponsor files, with a named owner and agreed upload cadence. Automatic sponsor downloading and licensed prices require separate evidence and a decision; no unapproved feed is a hidden prerequisite.
A reviewed price-upload field or separate small price source can satisfy the input contract if the Client agrees its provenance, refresh cadence and freshness labeling. A workbook snapshot alone cannot establish a current price. Broker-specific private prices must not become an unsourced shared price feed.
Track source-observed time, covered-through date, ingested time and published time separately. Re-uploading an old file does not make its data fresh. Frequency and expected announcement cadence affect history freshness; price freshness uses a declared market calendar and source SLA, not device time.
Before acceptance, choose price staleness threshold, announcement/history freshness thresholds, who refreshes each source and the unavailable/stale policy. Proposed policy: retain last known facts with dates and visible stale status, but do not label an old calculated figure “current.” Missing essential inputs return a typed unavailable reason.

## Verification, capacity and release

Domain tests cover leap-year window boundaries; local dates across device timezones; two same-month payments; special plus regular payments; missing/zero payouts; a changed/cancelled announcement; duplicate tickers; currency mismatch; split basis; incomplete trailing history; unknown frequency; stale and zero prices. Expected answers come from independently worked examples, not the implementation under test.
Integration tests use disposable real database/storage and exercise trusted admin success, normal-user denial, cross-user receipt denial, draft isolation, failed transaction, concurrent publication, identical retry, changed-content idempotency conflict, worker lease loss and outbox retry. Published read snapshots remain consistent during upload/publication/restore.
Browser tests perform upload → invalid report → corrected preview → publish → member chart/table and direct-link refresh. Verify no old fixture values survive and 24m selection truly covers the source window. Check mobile/desktop keyboard, screen reader, text enlargement and touch journeys with the readable baseline above.
Capacity planning uses the updated user scenario: private beta 2,500 users with 1,000 online simultaneously, then 10,000 launch users and a separate 300,000-active-user growth scenario. Online users are not equal to simultaneous API requests. Mobile still creates server traffic; foreground refresh, retry storms and chart calls need a measured budget.
Use `../CAPACITY_AND_RELIABILITY.md` as the canonical aggregate beta workload. Allocate a proposed 25 reads/sec steady and 100 reads/sec of its resume burst to distribution endpoints while a bounded admin import runs, with 2 million synthetic event revisions for data headroom. These are workload components, not lower replacement release gates. Record cache hit/miss mix and browser/mobile retry behavior.
Shared read budget: p95 <=500ms, p99 <=1.5s and <0.5% unexpected 5xx under the declared workload. Separately measure cold cache, publication invalidation and source outage; do not hide origin overload behind a cache-only result. Track database query counts/pool pressure and job throughput before choosing hosting spend.
Observe API latency/errors, import queue age/duration/failures, rows quarantined, stale sources/prices, unresolved listings, publication conflicts and metric-unavailable reasons. Logs include actor/request/job/release IDs but omit raw workbooks, personal holdings and full cell contents. Alert on missed source cadence and exhausted retries with an assigned owner.
Release requires A01–A10 evidence, accepted source coverage/format inventory, agreed yield and freshness policy, real reviewed data, authorization proof and a demonstrated restore. Missing upstream source history is an explicit acceptance exception requiring Client review, never a reason to claim complete 24-month coverage.
Rollback reactivates a valid release, recomputes affected metric/cache versions and records who did it; it never erases the original import or source document. Deploy/schema changes follow expand-and-contract compatibility and M1 recovery gates. Retain the prior API shape until web/mobile consumers can upgrade.

## Decisions and external prerequisites to close

- Which catalogue listings require history at launch, what actual history exists, and what exceptions apply to newer/uncovered funds? The contract gives a window but not a sponsor coverage inventory.
- Who supplies and may redistribute each sponsor file, which formats are in scope, and who owns ongoing updates? “Sponsor normalization” requires representative files, not guessed columns.
- Which yield is the primary “current” metric, what cash classifications are included, and how are splits/noncash events handled?
- Which source supplies compatible prices, on what cadence and terms, and what stale thresholds/market calendar govern the display?
- Does the first dashboard need a portfolio context or only fund history? Actual receipts remain M2-owned; export and automatic sponsor retrieval are not silently added to signed scope.
